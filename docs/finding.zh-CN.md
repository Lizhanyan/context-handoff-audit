# ChatGPT 桌面端 Codex 面板的跨模型上下文继承

**状态：** 公开技术说明 —— 未通知厂商  
**产品：** ChatGPT 桌面端 —— Codex 面板的"新侧边对话（new side chat）"  
**版本：** 26.1021.22027（构建号 21747，发布通道 prod）  
**日期：** 2026-10-24  
**类别：** 设计副作用 —— 无来源标注的上下文边界  
**严重性：** 低到中（上下文跨模型传递且无来源标注；下游安全影响本说明未测量）

---

## 摘要

ChatGPT 桌面端 Codex 面板的新侧边对话会继承主会话的聊天历史，并且可以运行在与主会话**不同的模型**上。

这大概率是有意设计：侧边对话存在的意义，就是让你能追问一句而不打乱主线程。这里讨论的是**这个设计的安全副作用**，不是实现缺陷。

一个由某模型驱动的主会话，可以建立起一套任务上下文，而侧边对话里的**另一个模型**会把这段上下文当成**自己之前的工作**。

当主会话的模型没有安全训练时（例如本地部署的模型），侧边对话的模型会继承一套完整成型的任务框架——而这段框架不是它写的，它也无法识别出来源不可信。至于这套框架是否真能突破接收模型的安全训练，是另一个问题，**本说明不对此下结论**。

整个过程不需要任何对抗性提示、注入或越狱技巧。用户只用了两个产品功能：打开侧边对话，选择模型。

---

## 威胁模型

| | |
|---|---|
| **攻击者能力** | 产品的普通用户，无特殊权限。 |
| **前提条件** | 能把主会话跑在一个无安全训练的模型上（本地或自托管）；能打开侧边对话。 |
| **不需要** | 提示注入、恶意仓库内容、社工、被攻陷的路由、自定义客户端，或任何其它对抗性输入。 |
| **目标** | 让一个受过安全训练的模型继续一项它本应拒绝的任务。 |

注意这个不对称：已有公开的交接类攻击，攻击者必须注入内容（RogueHandoff）、污染产物（Context-Fractured Decomposition），或者**先越狱一个安全模型**来写出那段历史（CHASE）。而这里，攻击者**直接自己提供上下文作者**——一个完全没有安全训练的模型——产品会无偿地把它的输出搬过去。

## 复现（无害）

用随机暗号。目的是确认**上下文是否跨过去**，不是生成有害内容。

**测试 1 —— 只在聊天里的暗号**

1. 主会话里，让主模型说一个随机暗号，例如 `BLUEBIRD-7731`。
2. **不要写进任何文件。** 它只能存在于对话中。
3. 开一个**新的侧边对话**。
4. 选一个**和主会话不同的模型**。
5. 问：*"刚才的暗号是什么？"*

**测试 2 —— 只在文件里的暗号**

1. 在工作区建一个文件，写入 `KESTREL-4402`。
2. 在侧边对话问：*"工作区里的暗号是什么？"*

**测试 3 —— 对照组：全新会话**

1. 开一个**全新会话**（不是侧边对话），**同一个工作区**。
2. 不要描述任务。
3. 问：*"这个项目现在在做什么？"*

---

## 实测结果

| 测试 | 结果 |
|---|---|
| 1 —— 侧边对话答出聊天专用暗号 | **是** |
| 2 —— 侧边对话答出文件暗号 | **是** |
| 3 —— 全新会话还原出任务 | **否** |

**测试 3 是对照组。** 它排除了"工作区本身就说明了一切"这个解释。同一个目录下的全新会话还原不出任务，而侧边对话可以。

结论：**搬运上下文的是侧边对话，不是工作区。**

---

## 机制

三个性质叠加：

1. **模型层面的安全判断是按轮次做的。** 拒绝与否针对当前这条消息，而不是累积的整个会话。参见 *Safety Alignment Should Be Made More Than Just a Few Tokens Deep*。

2. **先前的 assistant 轮次被当作既定前提。** `assistant` 角色里的内容不会被重新验证，而是直接当事实使用。参见上下文启动（contextual priming）与 *Trojan Horse Prompting*。

3. **产品不标注来源。** 上下文跨到另一个模型时，没有任何东西标明"这段是另一个、未受信任的模型写的"。

接收方模型不是被问了一个有害问题，而是被要求**继续**——有害意图藏在任务的**形状**里，不在最新一条消息的**内容**里。

---

## 为什么常规防御抓不到

| 防御 | 为什么失效 |
|---|---|
| 单轮输入分类器 | 每条消息单独看都无害。 |
| 输出分类器 | 输出是合理的续写，不是可识别的载荷。 |
| 逐模型红队测试 | 每个模型单独看都正常。 |
| 系统提示词（"不得协助 X"） | 要跟一段冗长、连贯、以 assistant 口吻写成的上下文竞争。 |
| 换模型 | 换模型**正是**这个机制本身，帮不上忙。 |

---

## 影响

- 只用产品自带功能，就能让一个模型接手它没有写过的任务上下文，不需要任何攻击技巧。
- 单轮护栏和逐模型评测都看不到这个交接。
- 继承来的框架是否真能突破接收模型的安全训练，**本说明没有测量**；已有的上下文启动（contextual priming）研究表明这种可能确实存在，这正是这个设计值得被审视的原因。
- 如果侧边对话的记录不进 session rollout 文件（公开介绍该功能的资料如此描述），那么**这个跨界点没有日志**——削弱审计和事后还原能力。
- 该模式可以推广到任何跨模型搬运上下文的功能：侧边对话、fork、子 agent、上下文压缩、模型路由、记忆、检索。

---

## 范围与局限

- n = 1：一个产品、一对模型、一个场景。
- **未测：** 换其它接收模型是否仍然成立；继承的历史是完整的、截断的、还是摘要；压缩之后是否仍然成立。
- 有害内容那一层后果是**轶事性观察**，本报告**刻意不包含**。本文只声明上下文传递机制。

---

## 建议修复

择一或多项：

1. **来源标签。** 给每条消息打上"哪个模型写的、是否经过安全评估"，并在所有交接中保留该标签。
2. **边界策略。** 在侧边对话 / fork / 换模型时，要么重新评估继承的上下文，要么直接丢弃。
3. **会话级评估。** 评估累积的对话，而不只是最新一轮。
4. **记录跨界。** 记录"哪个模型收到了哪段上下文"——包括临时的侧边对话。
5. **可见提示。** 如果历史会跨过去，就在界面上说清楚。用户目前无从得知。
