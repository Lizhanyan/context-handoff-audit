# 怎么防：上下文交接的防御

[English](defense.md)

本仓库描述的失效，位置在**产品边界**，不在任何单个模型内部。任何只盯一个模型、或只盯一条消息的防御，都会漏掉它。

本文按"防御住在哪一层"来组织，并且明确说明每一项到底买到了什么。

## 1. 模型层——必要，但不充分

模型厂商能做的：

- **评估累积的会话，而不是最新一轮。** 拒绝应该是整段对话的函数，而不是当前这条消息的函数。
- **用"继承上下文"的数据训练。** 训练样本里要有"有害框架出现在前几轮、或出现在 `assistant` 轮"的情形，不能只有"出现在最后一条用户消息"。
- **让模型对来源敏感。** 教它把"这段上下文不是我写的"当成一个有意义的信号。

做不到的：

- **来源不在 token 流里，模型就看不见。** 产品不打标，模型就没有东西可以推理。
- **重新训练很慢**，每次发版都清零。
- **本地部署的、没有安全训练的模型，谁都补不了。** 它按定义就在厂商的触达范围之外。

## 2. 产品层——问题真正住的地方

每一个把上下文跨模型边界搬运的功能，都是一个策略执行点：

- 侧边对话
- fork / 分支
- 子 agent
- 上下文压缩与摘要
- 同一线程内换模型
- 记忆与检索
- 会返回模型生成文本的 MCP 工具

对每一个功能：

| 控制项 | 含义 |
|---|---|
| **来源标注** | 每条消息都带上：作者模型、信任等级、是否经过安全评估 |
| **改写时保留标注** | 压缩摘要必须携带它所概括内容的来源 |
| **边界策略** | 交接时，要么重新评估继承的上下文，要么直接丢弃 |
| **记录跨界** | 记下"哪个模型收到了哪段上下文"——包括临时的侧边对话 |
| **界面提示** | 告诉用户历史会跨过去，以及跨给哪个模型 |

最后一条比听起来重要。今天用户根本无法判断：一个侧边对话是继承了历史、继承了摘要、还是什么都没继承。这是一个被静默做出的设计决定。

## 3. 组织层

- **盘点交接点。** 多数团队清楚自己用了哪些模型，但不清楚自己的边界在哪里。
- **按信任等级给模型分类。** 自托管、去掉了安全训练的模型，默认归入不可信一类。
- **定策略：** 哪一类模型写出的上下文，允许被哪一类模型接收。
- **留审计轨迹**，足以在事后还原一次会话——包括其中的交接。
- **红队打边界，不要只打模型。** 逐个 agent、逐个模型测试会给你虚假的安全感：每个组件单独看都表现正常。

## 每项措施实际买到了什么

| 防御 | 抓得到 | 抓不到 |
|---|---|---|
| 会话级安全评估 | 跨轮累积的意图 | 模型看不见的交接 |
| 来源标注 | 核心混淆："这段是谁的上下文" | 打标之前产生的旧记录 |
| 边界重新评估 | 不该跨过去的继承上下文 | 本身仍是单轮的重新评估 |
| 日志 | 事后还原 | 实时什么都拦不住 |
| 界面提示 | 意外 | 不看提示的用户 |
| 模型重新训练 | 已知的模式 | 新出现的交接方式、本地模型 |

## 什么不管用

- **单轮输入分类器。** 每条消息单独看都无害。
- **输出过滤器。** 输出是合理的续写，不是可识别的载荷。
- **逐模型红队测试。** 每个模型单独看都正常。
- **提示词层面的指令。** 要跟一段冗长、连贯、以 assistant 口吻写成的上下文竞争。
- **换模型。** 换模型是机制，不是缓解。

## 一份实用清单

对一个用多个模型共享上下文的产品：

- [ ] 列出每一个会在模型之间搬运上下文的功能。
- [ ] 逐个确认：它继承历史吗？全部、窗口、还是摘要？用户看得见吗？
- [ ] 逐个确认：继承来的上下文标注了作者吗？
- [ ] 有没有任何策略区分"受过安全训练的模型"和"没有的"？
- [ ] 跨界有日志吗？
- [ ] 压缩后的摘要，有没有继承它所替代内容的来源？
- [ ] 有没有人测过**交接**，而不只是测模型？

## 开放问题

1. **来源不在 token 流里。** 必须由产品加上去，而且没有通用格式。
2. **签名会话历史没有标准**——没有任何东西能阻止一段记录被当成另一个模型的作品来呈现。
3. **压缩会毁掉来源**，除非摘要被显式标注。
4. **跨厂商交接没有共同的信任词汇。** "可信"在两边含义不同。
5. **本地模型在所有厂商的可控范围之外**，所以任何厂商侧的加固都够不到它。
